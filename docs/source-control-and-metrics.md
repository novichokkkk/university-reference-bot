# Управление исходным кодом и метрики качества

## Платформа и инструменты

Исходный код проекта хранится в GitHub.

- IntelliJ IDEA — среда разработки;
- Java 21 — язык программирования;
- Spring Boot — каркас приложения;
- Maven — сборка и управление зависимостями;
- PostgreSQL — основная база данных;
- JUnit — модульные тесты;
- Checkstyle — статический анализ Java-кода;
- JaCoCo — измерение покрытия кода тестами;
- GitHub Actions — автоматизация сборки и проверок.

## Стратегия ветвления

Используется GitHub Flow:

- `main` — стабильная ветка проекта;
- `feature/<name>` — ветки разработки отдельных функций;
- изменения попадают в `main` только через Pull Request;
- после успешного слияния рабочая ветка удаляется.

Примеры веток:

```text
feature/telegram-handler
feature/database-layer
feature/testing
```

## Правила коммитов

Сообщения оформляются по Conventional Commits:

```text
feat: add telegram command handler
fix: correct database connection
test: add service tests
docs: update project documentation
ci: configure GitHub Actions
```

Workflow `commitlint.yml` проверяет сообщения коммитов при каждом Pull Request.

## Слияние изменений

1. Создаётся ветка `feature/...`.
2. Выполняются изменения и создаётся коммит.
3. На GitHub открывается Pull Request в `main`.
4. GitHub Actions запускает сборку, тесты и Checkstyle.
5. После зелёных проверок Pull Request объединяется с `main`.

## Контроль качества

Workflow `ci.yml` выполняет команду:

```bash
mvn verify
```

Команда запускает тесты, Checkstyle и сборку JAR-файла. Результаты сохраняются в Artifacts GitHub Actions.

## Метрики

Автоматически собираются следующие метрики:

1. количество нарушений Checkstyle;
2. покрытие строк кода тестами JaCoCo;
3. общее количество тестов;
4. количество упавших тестов;
5. время выполнения тестов;
6. количество коммитов.

Workflow `metrics.yml` запускается при создании тега этапа вида `stage-e1` и сохраняет CSV-файл с результатами в Artifacts.

## Релиз

Стабильная версия создаётся тегом, например:

```bash
git tag -a v1.0.0 -m "Release v1.0.0"
git push origin v1.0.0
```

После этого на GitHub создаётся Release `v1.0.0` с описанием изменений и JAR-артефактом.
